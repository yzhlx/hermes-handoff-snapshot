# 数据主权交付：导出与账号删除

2026-10-02（Asia/Shanghai，延续 10-01 任务）。本批实现 `03-数据与接口契约.md` §9 的数据主权能力：**导出自己的记录**与**两段式账号删除**。对齐 FR-053（导出/删除是用户主权）与 `03` §2 的 `account.status`。**不是完整产品交付，也不是生产发布。**

## 本批范围与依据

在此之前，`03` §9 明确写着"导出与账号删除是需落实的规划能力，不宣称本文实现"。用户没有任何办法把自己的记录带走，也没有任何办法要求删除——而 `03` §2 早已定义了 `account.status: active/deletion_pending/deleted`，代码里却连这个字段都不存在。

| FR | 原节 | 本批产出 |
|---|---|---|
| FR-053 | 53 最终产品体验 / 03 §9 | 导出包（结构化 JSON + 数据字典 + 带 sha256 的附件清单）与私有短期下载 |
| 03 §9 / §2 | 账号删除规划 | 两段式、可撤销的删除生命周期，登记后学习写入暂停，最终清除并保留最少墓碑 |

## 核心设计

`PASS`：**导出只带走你自己的东西**。`POST /account/exports` 生成的文档包含：该账号在全部 27 张 owner 作用域表中的行（密钥列剔除）、数据字典（每张表导出了哪些列）、附件清单（id/原名/MIME/字节/`sha256`/状态）。**绝不导出** `password_hash`、`token_hash`、`csrf`、`object_key`，也绝不包含他人数据。下载私有且短期（`expires_at`，到期返回 410），不提供永久公开 URL。

`PASS`：**删除是两段式，且在"还能撤销"与"真的执行"之间有明确分界**。第一次确认（逐字输入 `DELETE MY ACCOUNT`）登记请求，账号进入 `deletion_pending` 并**暂停学习写入**（403 `ACCOUNT_PENDING_DELETION`）；撤销（需 `If-Match`）回到 `active`，一切照旧；**再次**逐字确认才执行清除。把不可逆动作藏在一次误点够不到的地方，同时不靠弹窗吓唬人。

`PASS`：**清除范围与隔离边界都经过验证**。清除按 `Base.metadata.sorted_tables` 的**子表优先**顺序删除全部 owner 作用域行（含导出包），然后保留最小墓碑：`account_deletions` 一行（`completed`）+ `users.status='deleted'` + 用随机哈希替换 `password_hash`（凭据作废）+ 释放用户名。其他账号的数据一行不动。**墓碑那张表本身被排除在清除之外**——否则清除会把自己的记录也删掉。

`PASS`：**登记后仍能自救**。账号级端点（导出、撤销、再次请求）走的是不含待删除写入封锁的依赖：用户在删除前还能导出、能撤销。这是实现过程中发现并修正的设计点——最初把封锁做在共享依赖上，会导致"想删之前先导出"和"想撤销"都被挡住。

`PASS`：**清除完成即失能**。登录会话随清除消失，凭据被替换为随机哈希，`identity` 对 `status='deleted'` 直接 401——已删除账号无法再认证。

## 过程中发现并修正

- **真实浏览器验证抓到一个 500 缺陷**：打开书房会分配当日金句，`daily_quotes.local_date` 是 `Date`（不是 `DateTime`）类型，导出序列化只处理了 `datetime`，于是第一次在浏览器里点"生成导出包"直接 500。**单元测试没抓到它**，因为测试账号没有金句记录——这正是"必须做真实应用验证"的价值。已修复（`isinstance(value, date)` 覆盖两者）并补了一条端到端回归测试（先 `GET /home` 再导出）。
- **"待删除写入封锁"最初挡住了自救路径**：封锁放在共享写依赖上后，待删除账号既不能导出也不能撤销。改为账号级端点走 `sanitized_write`，学习写入仍被 403 挡住。
- **清除曾把自己的墓碑删掉**（503）：`account_deletions` 也有 `owner_id`，按通用规则会被清除。加入 `PURGE_KEEPS` 排除它。
- **两个既有迁移测试因新增 `users.status` 列而失败**，属"旧 schema 不该用当前 ORM 播种"：`test_comparison_storage` 与 `test_suggestion_storage_review` 用 `User(...)` ORM 往旧版本 schema 里插数据，新列随之出现在 INSERT 中。改为原生 SQL 只写当时存在的列（与 `test_attachment_migration_review` 既有惯例一致）。另外 `test_comparison_storage` 那条测试把**schema 也哈希**进快照却升级到 `head`，任何后续新增列都会使其失败；已把升级目标限定到它自己声称验证的 `0010`，断言才与测试名一致。未降低任何断言，未隐藏任何失败。
- 首次跑真实 HTTP 验证时 2 项失败是我**脚本期望值写错**（把 `record_count` 当成只数题目，忽略了 bootstrap 预置的 5 个学科）；改为"我加一条则 +1、别人加一条则不变"的增量断言，更准确。

## 限制与下一步

`KNOWN LIMITATION`：**撤销窗口与备份留存仍是命名常量**（`REVOKE_WINDOW_HOURS=24`、`EXPORT_TTL_HOURS=24`）。`03` §9 明确这两项"待部署评估确定"，在承诺"已永久删除"前必须处理备份边界——目前**没有生产备份**，所以这个承诺在本机环境里是成立的，上生产前必须重新评估。

`KNOWN LIMITATION`：**导出尚未覆盖原始附件字节**。契约建议"带校验清单的原始附件"，当前导出包含附件清单（含 `sha256`）但不含附件二进制本体；私有附件下载端点仍可逐个取回。打包附件属后续项。
