# 旧项目证据审计

检查日期：2026-09-30。基线：work/local-setup，83447ca。仅检查文件与源码；未运行旧应用、测试、数据库迁移或性能压测。

## 已观察的事实

| 证据 | 观察 | 对重写的影响 |
| --- | --- | --- |
| 根目录 Dockerfile | 云端容器只复制 cloud_hermes 与 web | 部署入口与桌面应用入口不同，必须确定唯一新版入口 |
| web/index.html | 云端首页以对话、云端任务、本地节点为主 | 与新需求的金句、学科、方法及学习闭环首页不同 |
| outputs/learning-os-app.html | 同时加载应用、UI修补、错题、动量及手写模块 | 有多个职责入口；仅此事实不足以证明质量差或性能差 |
| cloud_hermes/db.py | 云端使用 SQLite，包含对话、任务、执行节点等表 | 旧数据模型与新学习会话、答题证据模型需重新映射 |
| CURRENT-STATE.md | 文档标注 2026-07-22，旧分支与旧提交 | 不应当作当前克隆的运行状态证明 |
| AGENTS.md | 旧规则强调本地 Windows、单用户、SQLite等边界 | 用户本次已明确新版云端；新项目规则必须独立说明云端范围 |
| 功能.md | 新定位为自主选择的数字书房，明确不要强制任务 | 需要以新需求整理功能，不能机械保留旧任务主导体验 |

## 结论及限制

可以确认存在产品方向、入口和历史状态文档混杂的问题。尚未证明性能、数据库可靠性、所有 UI 行为或整个代码质量有缺陷。不能仅凭文件多就宣判全部代码不可用。

建议新项目以需求和契约重建实现，不逐文件照抄；旧项目保留为事实和数据来源。重写能统一边界，但同样可能重新引入问题，因此必须先用一个真实可用的跨设备闭环验证方案。

若未来需要迁移，另行只读盘点实际数据库版本、记录数量、附件与用户归属。历史报告的 PASS 不等同于本次执行通过。
